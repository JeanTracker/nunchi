발견 사항영향과 조건보완 방향
같은 홈과 같은 ID높음 · 재현키에 공급자 정보가 없어 analysis.json, want, 작업, 잠금이 한 위치를 가리킵니다. 같은 UUID가 정상 실행에서 우연히 겹칠 가능성은 낮지만, 공용 관제 홈의 설계에서는 공급자 구분이 필요합니다.기존 홈을 유지하거나 공용 홈에는 provider + session_id를 큐·잠금·상태·결과의 공통 키로 사용합니다.
동일 Codex 세션 중복 재개코드상 가능성같은 Codex ID에서 SessionStart가 올 때마다 분석 설정이 다시 써집니다. 두 런처가 다른 모델로 같은 대화를 열 수 있는 조건이라면, 이후 분석이 마지막 시작의 모델을 고를 수 있습니다.같은 세션을 여러 창에서 읽어도 모델 설정은 명시적으로 변경할 때만 갱신하는 계약을 둡니다.
대기열 갱신 시간차코드상 가능성새 Stop과 이전 요청 삭제가 같은 세션에서 겹치면, 파일의 내용 확인과 삭제 사이에 새 요청이 들어갈 수 있습니다. 임시 파일의 원자적 교체만으로 큐 읽기·수정·삭제 전체가 잠기지는 않습니다.세션별 잠금 아래 병합·소비하거나 세대 번호가 있는 작업 기록으로 최신 요청을 보호합니다.
빈 claim 파일의 시간차코드상 가능성워커가 .claim을 만든 직후 PID를 쓰기 전, 다른 워커가 빈 파일을 묵은 claim으로 판단해 삭제할 수 있습니다. 분석 중복 또는 같은 결과의 동시 저장 위험입니다.PID 문자열로 소유권을 판단하는 구간을 프로세스 수명에 붙은 세션별 OS 잠금으로 바꿉니다.

먼저 공용 키 충돌을 막고, 전환 전 실제 혼합 세션과 큐 경쟁을 따로 재현하는 게 적절합니다. 현재 평가는 각 기본 홈을 쓰는 미리 보기와 공용 관제 저장소를 도입하는 경우를 구분합니다. 세션과 분석 설정 · 작업 합치기·담당 워커 · 기존 워커 시험
